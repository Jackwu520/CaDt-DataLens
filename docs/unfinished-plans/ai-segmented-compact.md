# 分段压缩（会话超出模型输入上限时的自救压缩）

> 状态：**待实施**（2026-11-18 方案成文，未开工）
> 背景：实测——300 KB 级会话切到 256K 窗口模型后估算 121%：发送门禁拒发，整体压缩也一并无路，会话死锁，出路只剩切更大窗口模型或开新会话。
> 定位：`ai-compact.js` 整体压缩的**兜底扩展**——不改现有 `/compact` 与 auto-compact 的语义，只在「整体压缩不可行」（`compactBlocked`）时提供分段路径。
> 前置（已落地，2026-11-18）：发送门禁 `AI_CTX_SEND_BLOCK_RATIO`（90% 拒发）、`aiCtxBannerState.compactBlocked`（估算 ≥100%）、提醒条按钮 ≥100% 换「分段压缩」占位（点击提示未实装）、`startCompact` ≥100% 预拒。

## 1. 问题

会话估算 ≥ 模型窗口（100%）时的现状：

1. **发送**被门禁拒（90% 档），无争议；
2. **整体压缩**名义上是出路，实际不可行——见 §2 的两个独立死因；
3. auto-compact 只在阈值（默认 80%）触发后走同一条整体压缩链路，同样救不了；
4. 用户唯一操作是切回大窗口模型，但会话钉死的模型往往就是「这台机器上最大的」。

## 2. 为什么整体压缩救不了

**死因 A：压缩请求本身就是一次「全量发送」。** `buildCompactMessages` = 摘要 system + 整段会话转录一次发出。会话已 ≥ 窗口时该请求大概率被服务商拒收（input tokens 超限）——这就是 ≥100% 档在 `startCompact` 预拒的依据。

**死因 B（更隐蔽）：即使发得出去，摘要也是坏的。** `compactTranscriptOf` 有 `TRANSCRIPT_MAX = 120000` 字符的**尾部截断**硬上限。121% 会话（约 317k tokens）的转录远超 120k 字符，截断后摘要只覆盖最近一小段，**更早的内容静默丢失**——原文虽归档可查，但 `<conversation_summary>` 注入的是一份严重残缺的摘要，压缩后模型「失忆」。请求能成功反而更糟：没有报错，质量塌方无人察觉。

结论：≥100% 档需要一条**请求体积可控、原文不丢、摘要覆盖全量**的新链路，即分段压缩。

## 3. 目标与非目标

**目标**
- 估算 ≥100% 的会话在不切模型、不丢原文（归档不删除）的前提下，被压回可发送状态；
- 中途失败/取消/崩溃都停在一致状态，可重试续做；
- 段级进度可见、可取消。

**非目标**
- 不改 90% 发送门禁与整体压缩的常规语义（<100% 时一切照旧）；
- auto-compact 不自动走分段（V1 只人工触发：按钮或 `/compact`）；
- 不做跨会话/多会话压缩。

## 4. 方案

### 4.1 分段算法（纯函数，扩在 `ai-compact.js`）

输入：`messages`、`windowSize`、`segmentBudget`（默认 `windowSize * 0.6`，留 40% 余量给摘要器 system、合并请求与估算误差）、`keepTail`（沿用 `COMPACT_KEEP_TAIL`）。

- 复用 `computeCompactCutoff` 的回退思路按 **user 轮边界**切分——一轮（user → assistant → tool 结果…）绝不拆进两段；
- 工具调用与工具结果必须同段（assistant.toolCalls 与紧随的 tool 消息捆绑）；
- 从最老开始聚轮成段：再加一轮就超预算即成段；末段自然收尾；
- 最近的 `keepTail` 条不进任何段（压缩后仍留在正文，保证「当前正在做什么」在上下文里）。

产出：`segments[]`（每段含起止索引与估算 tokens）+ 纯函数可单测。

### 4.2 执行循环（运行时，主会话在 `ai-panel.js`）

摘要采用 **map + 一次合并**（质量优于滚动摘要：滚动会随段数衰减，合并请求输入只有各段摘要，体积很小）：

1. **map**：逐段 `AISendChat`——system 用分段摘要器提示词（新增常量，约束「只摘本段、保留事实/决策/未完成任务」），user = 本段转录（沿用 `compactTranscriptOf` 的渲染规则，按段截取不再触 TRANSCRIPT_MAX）；每段摘要 ≤ 2000 tokens；
2. **reduce**：全部段完成后一次合并请求——输入 = 各段摘要（顺序拼接）+ 焦点指令，产出最终 summary；
3. **落盘**：`applyCompactToSession`（现内核）写 summary 并裁剪 messages，被裁段走既有磁盘归档链路（`sessionStore.archiveSession`）——**真源永远不删**，导出 Markdown / 查看已归档消息照旧可查；
4. 复用压缩 oneShot 通道：`kind: 'compact'` 扩展 `mode: 'segment'`，看门狗/停止/流式 UI 全部白拿。

**每段完成即持久化**（崩溃恢复点）：该段消息先归档、段摘要先落 `session.summary` 草稿位——任何时刻中断，已完成的段都已安全收编，重试从下一个未完成段继续。

### 4.3 进度 / 取消 / 失败

- 提示行与工具卡显示「分段压缩 2/5」；
- **停止** = 停在安全中间态：已完成段保留，用现有部分摘要直接 apply（宁可摘要短、不回退已归档内容）；
- 单段失败沿用 aitransport 重试；重试耗尽即中止并提示「已完成 n/m，可再次点击续做」。

### 4.4 UI 联动（占位点已留好）

| 触点 | 现状（占位） | 实装后 |
| --- | --- | --- |
| 提醒条按钮（`updateCtxBanner`） | ≥100% 换「分段压缩」+ aria-disabled + 点击提示 | 同位置点击 → 启动分段压缩，按钮变「停止」语义随 oneShot |
| `/compact`（`startCompact` 预拒） | ≥100% 直接拒绝并指引切模型 | 自动转分段路径，焦点指令透传到合并请求 |
| 发送提示行 / flash | 「请切换更大上下文的模型」 | 补「或分段压缩」 |
| banner 文案（`aiCtxBannerState`） | 「已超过模型上限：请切换更大上下文的模型」 | 「已超过模型上限：请切换更大上下文的模型，或分段压缩」 |
| 完成后 | — | `updateCtxBanner` 自然回落，发送门禁解锁 |

### 4.5 子代理（V2）

`subCompacts` 走同一内核；子代理转录是展示层、与 messages 独立，分段只做内存裁剪、无磁盘归档，天然更简单。V1 不动。

## 5. 护栏

- 纯函数（`frontend/test/ai/`）：分段切轮 / 预算边界 / 工具调用-结果对齐 / 段摘要合并的形状断言；
- 接线：按钮占位 ↔ 实装切换、`/compact` 转发、进度文案；
- `aiCtxBannerState` 断言随文案演进同步改（本档测试已在 `ai-constants.test.mjs`）。

## 6. 风险与权衡

- **map 段数过多**：预算 0.6 控制段数（256K 窗口的 317k-token 会话 ≈ 3 段）；合并请求体积小，质量风险集中在段内摘要——分段器提示词要求保留「事实 / 决策 / 未完成事项」三类硬信息；
- **估算误差**（字符近似 tokenizer）：段预算留 40% 余量兜底；单段请求仍被拒时按失败重试→中止处理，不会留下半段状态；
- **耗时**：3 段 ≈ 3+1 次串行请求，进度可见、可取消，可接受；
- **原文安全**：全程只归档不删除，最坏情况（合并失败）= 拿到一份只覆盖部分历史的摘要，原文完整可查。
