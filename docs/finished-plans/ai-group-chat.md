# 智能体群聊：多轮讨论引擎、主持调度与任务协作（实施计划）

> 前置阅读：`docs/finished-plans/session-messaging.md`（会话信箱 / 后台注入）· `docs/finished-plans/ai-personalization.md`（人设与注入护栏）· `docs/unfinished-plans/side-chat-tab.md`（内容区虚拟文档标签页先例）· `docs/finished-plans/ai-head-agents-terminal.md`（多智能体 UI 先例）
> 范围：设置 → AI → 智能体；AI 面板群聊列表；内容区「群聊」标签页；`frontend/src/ai/ai-agent-*` / `ai-group-*` 新域；Go 侧新增 `ai-groups` 存储壳（复用 `internal/sessionstore` 引擎）；不改 AI 传输协议、不改现有会话存储格式、不新增 npm / Go 依赖

**一句话定位**：群聊不是「多个机器人排队回答用户」，而是**多智能体圆桌**——用户提出议题，若干不同人设/模型的 AI 在主持人调度下进行多轮讨论，最终产出可用的纪要（共识、分歧、决定、行动项）。

**关键设计转变**：

| v1（已否决） | v2 |
| --- | --- |
| @ 是唯一唤醒源，回完即停 | @ 是「请求发言 / 点名」；默认由主持人按轮调度，讨论可以持续多轮 |
| 防风暴靠砍对话（每条最多 @2、回完即止） | 防风暴靠**集中调度权**：主持制下成员不能直接唤醒别人，只能请求；轮次与预算是硬上限 |
| 成员各回各的，缺少相互回应 | 共享讨论看板（立场/共识/分歧/问题/任务）+ 主持人给下一位「发言焦点」，强制成员回应彼此 |
| 没有「讨论是否该结束」的判定 | 轮次预算 + 主持人收敛判定 + 用户随时介入 |
| 成果就是聊天记录 | 成果是结构化纪要 + 任务板，可复制、可带回会话 |

**两份数据，默认全量**：每个成员维护

1. **群聊数据**：所有成员最终发送到群聊的对话（共享、唯一真源，只有对话，不含思考链/工具调用）。
2. **私有数据**：自己的思考链、工具调用/结果、供应商原始过程（仅自己与用户可见，其他成员和主持人都不读）。

成员请求 = **全部群聊对话** + **自己的全部私有过程** + 系统规则/人设/看板摘要/当前焦点。默认不按条数截断（不是「最近 8–12 条」）。**共享群聊对话永不自动压缩**：装不下时该模型直接停止参与，等用户主动压缩群聊数据或换更大窗口模型；**只有私有过程会自动压缩**以适配窗口。常规模型按 **256K / 1M** 分档，窗口越大越晚遇到共享对话溢出。讨论看板是派生摘要，用于调度、UI 与纪要，**不是第三份真源**。

## 1. 产品定义：群聊用来做什么

先定用途，再定模式。群聊的默认用途是 **AI 圆桌讨论**，另外两个模式是同一引擎下的预设：

### 1.1 圆桌讨论（默认）

适合：方案评审、技术决策、头脑风暴、风险分析、多视角推演。

流程：

1. 用户给出议题（可附背景、约束、期望产出）。
2. 主持人开场：确认议题、拆出 2–5 个讨论子问题、建立讨论看板。
3. 按轮讨论：每轮每位成员最多一次实质发言；成员必须回应前一位的具体观点（同意/反对/补充/存疑），不能各说各话。
4. 每轮结束主持人做一次小结：已达成共识、仍存在的分歧、未决问题；决定是否再来一轮。
5. 讨论结束输出**纪要**：共识、分歧及双方理由、决定、行动项、未决问题。

默认 2 轮，可在 1–3 轮之间配置；主持人可在第 1 轮就判定收敛，提前结束。

### 1.2 任务协作

适合：把一个目标拆成可执行方案、分工、依赖梳理、交付物评审。

在圆桌引擎上增加：

- 主持人把目标拆成任务板（任务、负责人、状态、依赖、验收标准）。
- 成员围绕任务讨论：谁做什么、接口/依赖怎么定、风险在哪里。
- 任务 owner 在轮到自己时汇报进展/阻塞；主持人协调。
- 全部任务完成或明确 blocked 后，主持人汇总成方案/计划。

无工具时，任务产出以分析、方案、清单为主；G5 再评估只读工具。

### 1.3 自由群聊（可选，不是默认）

适合：角色扮演、闲聊、发散讨论、模拟多人对话。

- 无主持人或弱主持；成员可直接 @ 彼此。
- 保留 v1 的直接 @ 路由与全部硬上限。
- 用户 `@全体成员` = 每人回应一次，不自动无限接力。
- 这是「聊天室」，不是「会议」；不产出结构化纪要（可手动总结）。

### 1.4 辩论 / 评审（圆桌预设）

- 给成员分配角色：正方、反方、评审/裁判、领域专家。
- 主持人按「正 → 反 → 评审」交替安排，指定轮数；裁判最后给结论。
- 本质是圆桌 + 角色模板 + 发言顺序策略，不单独做引擎。

## 2. 为什么 v1 会变成「一问一答就结束」

v1 的调度是：

```
用户消息 → 解析 @ → 被 @ 的成员各回一次 → 没人被 @ → 结束
```

这套规则在防风暴上很有效，但它把「发言权」交给了消息里的 @，于是：

- 用户不 @ 时只有主持人回一句；
- 主持人回完没有 @ 别人，就结束；
- 成员即使有不同意见，也没有机制让它继续；
- `@all` 又被设计成「各回一次、不互相接力」，进一步压扁讨论。

**修正原则**：把「谁来说下一句」从消息文本里拿出来，交给一个**调度者**。调度者可以按轮安排、可以要求成员回应彼此、可以决定继续或收敛。这样讨论可以很长，但同时在飞的发言始终有界，广播风暴不会发生。

## 3. 讨论引擎（核心）

### 3.1 角色

| 角色 | 职责 | 是否参与辩论 |
| --- | --- | --- |
| 用户 | 提出议题、随时插话、点名、暂停/继续/结束 | 是（作为用户消息） |
| 主持人（chair） | 建立议程、决定下一位发言者与发言焦点、更新讨论看板、判定收敛、输出纪要 | **不参与**（默认独立主持人；也可配置为某位成员兼任） |
| 成员（participants） | 按主持人的安排发言；回应他人；输出结构化立场 | 是 |

主持人有三种来源：

1. **AI 独立主持人（默认）**：设置里可创建一个「主持人」智能体（独立模型，建议用便宜/快的模型），群设置里选它；它不在成员名单里，不参与讨论。
2. **成员兼任主持人**：选一位成员当 chair；省一次模型配置，但可能偏向自己的观点。
3. **用户主持**：不做 AI 调度，用户在 UI 里手动点下一位；适合想精确控制或省钱。

> 默认推荐「AI 独立主持人」。它只做调度与纪要，不站队，能保证每个成员都被听到。

### 3.2 讨论状态（共享看板）

讨论的上下文默认就是**全部群聊对话**；看板是派生摘要，用于主持人调度、用户查看和生成纪要，不是对话的替代品：

```json
{
  "topic": "是否把会话存储改成独立 ai-groups 根",
  "goal": "decide",
  "agenda": ["写锁边界", "迁移成本", "回滚方案"],
  "round": 1,
  "maxRounds": 2,
  "positions": [
    {"agentId": "agent-a", "stance": "agree", "keyPoints": ["隔离更安全"], "concerns": ["存储清理要同步"], "updatedAt": 0}
  ],
  "agreements": ["群聊数据独立目录更安全"],
  "disagreements": [
    {"point": "是否需要迁移脚本", "sides": ["agent-a", "agent-b"], "status": "open", "resolution": ""}
  ],
  "openQuestions": ["旧群聊数据怎么处理？"],
  "decisions": [],
  "actionItems": [
    {"id": "t1", "title": "补存储清理条目", "ownerId": "agent-b", "status": "todo"}
  ],
  "coveredPoints": ["已讨论独立目录的隔离收益"],
  "floorRequests": [
    {"from": "agent-a", "to": ["agent-b"], "reason": "希望 B 回应迁移成本"}
  ],
  "lastRoundSummary": ""
}
```

- 每位成员发言后输出一个结构化 `group` 块（见 §3.5），运行时把立场、要点、疑问、任务合并进看板，**不额外调用模型**。
- 成员在 `groupBlock.handoff` 里的请求进入 `floorRequests`；主持制下它不是直接唤醒，而是轮到主持人复盘/排下一轮时的参考（§3.6）。
- 每轮结束由主持人审阅/修正看板并写小结（一次调用）。
- 下一位发言者的请求 = **全部群聊对话** + **自己的私有过程** + 看板摘要 + 主持人焦点；因此它知道别人说过什么、自己该回应谁，也不会重复。
- 用户可以在「讨论看板」抽屉里实时看到：议程、每人立场、共识、分歧、未决问题、任务；讨论结束时直接变成纪要。

### 3.3 讨论循环

```
开始讨论（用户给出议题）
  │
  ├─ 主持人开场：确认议程 → 生成第 1 轮发言计划
  │
  ▼
for round in 1..maxRounds:
    按本轮计划依次发言：
      成员收到：看板摘要 + 本轮焦点 + 最近几条发言
      成员输出：正文 + group 结构化块（立场/要点/疑问/handoff）
      运行时合并看板；渲染/落盘
      预算/用户停止检查
    主持人轮末复盘：
      更新看板、写本轮小结、决定「继续 / 收敛 / 结束」
    若收敛或达到预算：break
  │
  ▼
主持人输出最终纪要（可由看板生成，也可让主持人润色一次）
```

- **发言计划**解决成本：主持人一次决定本轮「谁、按什么顺序、各自回应什么」，而不是每说一句就调用一次主持人。
- **轮末复盘**解决质量：主持人看到整轮发言后统一更新看板、指出分歧、决定下一轮；成员不会因为没人 @ 就沉默。
- 用户随时插话：消息作为新的用户输入进入看板/下一轮焦点；默认不打断当前发言，当前成员说完后由主持人吸收。

### 3.4 主持人的两种策略

| 策略 | 调用次数 | 适用 | 行为 |
| --- | --- | --- | --- |
| **轮计划 `round-plan`（默认）** | 每轮 1 次计划 + 1 次复盘 | 圆桌、评审、头脑风暴 | 一次给出本轮发言顺序与每人焦点；轮末统一复盘 |
| **逐句调度 `adaptive`** | 每次发言前后各 1 次 | 辩论、任务协作、需要临场追问 | 每说完一位，主持人根据新信息决定下一位；更自然但更贵 |

- 默认 `round-plan`：4 位成员 × 2 轮 ≈ 8 次成员发言 + 4 次主持人调用 + 1 次纪要 ≈ 13 次调用；`adaptive` 约 17–20 次。
- UI 在创建群聊时显示预计调用量，并提供「轻量 1 轮 / 标准 2 轮 / 深度 3 轮」预设。
- 主持人模型可独立配置，建议用便宜模型；用户可切换为「用户主持」零 AI 调度成本。

### 3.5 成员结构化输出（`group` 块）

每位成员的回复末尾可以带一个围栏块（主持人也会用同一协议）：

````markdown
```group
{
  "stance": "disagree",
  "keyPoints": ["独立目录增加一套存储清理逻辑"],
  "concerns": ["旧数据迁移需要一次性脚本"],
  "questions": ["回滚时旧版本还能读到群聊吗？"],
  "handoff": ["迁移负责人"],
  "agendaItem": "迁移成本"
}
```
````

- `stance`：`agree / disagree / supplement / question / neutral`。
- `keyPoints / concerns / questions`：短句，每条 ≤200 字符；运行时合并进看板。
- `handoff`：**请求**某人回应（不是直接唤醒）。主持制下由主持人决定是否采纳；自由模式下才是直接接力。
- `agendaItem`：本条发言对应哪个子问题；用于看板归类与避免跑题。
- 块本身在 UI 里渲染成轻量「立场卡」；不把 JSON 原文显示在正文。
- 解析失败不影响正文，只丢结构化信息并记一条系统事件。

### 3.6 主持人的 JSON 契约

主持人的每次调用返回严格 JSON（或带一个 `group` 围栏），运行时校验：

```json
{
  "chairMessage": "第 1 轮结束：大家在隔离收益上一致，分歧在迁移成本。请 B 先回应回滚风险。",
  "plan": [
    {"speaker": "B", "focus": "回应 A 的迁移成本担忧，给出回滚方案", "agendaItem": "迁移成本"},
    {"speaker": "C", "focus": "补充存储清理的改动点", "agendaItem": "写锁边界"}
  ],
  "statePatch": {
    "agreements": ["..."],
    "disagreements": [{"point": "...", "sides": ["A", "B"]}],
    "openQuestions": ["..."],
    "actionItems": [{"title": "...", "owner": "B", "status": "todo"}]
  },
  "roundComplete": true,
  "done": false,
  "minutes": null
}
```

- `plan` 为空且 `done=false`：主持人认为本轮无需继续，运行时让主持人再判定一次或结束。
- `done=true` 时必须给 `minutes`（或运行时用看板生成纪要，见 §3.8）。
- 解析失败/超时：回退策略——按「本轮未发言成员顺序」执行，轮末再请主持人复盘；连续两次失败则暂停并提示用户。
- 主持人不能指定非成员、被静音成员、模型失效成员；运行时过滤并记系统事件。
- 主持人不得让同一成员在同一轮发言两次（除非用户明确要求追问）。
- 主持人输入包含看板里的 `floorRequests`；采纳则写进 `plan`，不采纳则保留供下轮参考。**用户点名优先级最高**，可直接覆盖 `floorRequests`。

### 3.7 轮次、收敛与结束

一轮的定义：**每位可用成员最多一次实质发言**；主持人可以跳过「本轮没有新信息」的成员，但要在看板里标注。同一成员连续两轮无发言时，看板/状态条提示用户（可点名或移除），不静默。

结束条件（任意一个）：

1. 主持人判定收敛（无新分歧/未决问题，或所有议程项已覆盖）。
2. 达到 `maxRounds`（默认 2，硬上限 3）。
3. 达到 `maxSpeeches`；或手设了 `maxTokensPerDiscussion > 0` 且达到该值。
4. 用户暂停并结束，或点「结束并总结」。
5. 连续一整轮没有任何成员输出新要点（运行时根据看板变化判定，主持人复核）。

结束动作：

- 主持人输出**最终纪要**：
  - 议题与目标
  - 共识（带理由）
  - 分歧（双方观点、是否已解决）
  - 决定
  - 行动项（负责人/状态，可一键转成任务板）
  - 未决问题
- 纪要以卡片形式插在群聊末尾，可复制、导出 Markdown、带回某个 AI 会话。
- 讨论记录仍完整保留在 transcript；纪要是结构化摘要，不是替代。

### 3.8 纪要的两种生成方式

| 方式 | 调用 | 说明 |
| --- | --- | --- |
| 看板模板（默认） | 0 次 | 用讨论看板直接渲染纪要；快、便宜，格式稳定 |
| 主持人润色 | 1 次 | 让主持人根据看板 + 关键发言写成自然语言纪要；适合要发给别人看的场合 |

### 3.9 用户的介入方式

- **随时发言**：消息进入讨论；主持人下一轮计划会吸收（若在轮中，当前成员说完后生效）。
- **点名**：`@A 请回答 X` → 主持人下一次计划**必须**把 A 放进计划（A 不可用时提示）。
- **@全体成员**：主持人安排所有可用成员在下一轮各发言一次（不是「各回一句就结束」）。
- **命令/按钮**：`暂停`（当前发言完停）、`继续`（新增一轮，受硬上限）、`结束并总结`、`投票`（主持人组织表态并统计）、`压缩群聊数据`（用户主动生成共享摘要）。
- **我来主持**：切换到用户主持模式；UI 显示「下一位发言」选择器和焦点输入框；AI 主持人暂停调用。
- **插话不打断**：默认当前成员说完再吸收；用户点停止则立即中断全部在飞请求。

### 3.10 异构模型是常态：能力矩阵

群成员可能来自不同账号/服务商，上下文窗口、输出窗口、是否思考、响应速度都不同。运行时在群创建/成员变更时，从 `modelEntry` 推导一份能力快照（不落盘为配置，随模型配置变化）：

| 能力 | 来源 | 用途 |
| --- | --- | --- |
| 上下文窗口 | `entry.contextWindow` | 计算该成员的请求预算；常规按 256K / 1M 分档，低于 256K 走紧凑档并标黄 |
| 输出窗口 | `entry.outputWindow` | 预留输出；思考预算另计 |
| 是否思考 | `entry.thinking`（Anthropic）/ `entry.reasoningEffort` 非空（兼容 OpenAI） | 选择超时档、UI 徽标、成本提示；**主持人也可以思考** |
| 上下文预算档 | 由窗口推导 1M / 256K / 兜底 | 决定**共享对话溢出/私有过程压缩的阈值**，不决定固定条数；默认全量 |
| 测速 | 运行时统计 TTFT/总时长（内存） | 消息旁显示、估算本轮耗时；不承诺跨重启 |
| 账号/服务商 | `profileId` | 并行轮的按账号并发限制、429 归属 |
| 手动覆盖 | `agent.slowTier`（智能体布尔） | 兼容端点不暴露 reasoning 时手动按思考/慢速档计时；超时档与预检徽标同步采用 |

UI：成员行显示 `256K`、`1M`、`思考`、速度徽标；群创建时给出兼容性预检。**不同模型不要求相同上下文**——共享的是全部群聊对话，各自按窗口决定何时溢出/压缩自己的私有过程。

### 3.11 窗口策略：共享对话不自动压缩，私有过程可压缩

`buildMemberContext(member, sharedLog, privateLog, board, focus)` 每次发言前按该模型预算估算：

1. 系统规则 + 人设 + 看板 + **全部共享群聊对话**（不压缩）。
2. **自己的私有过程**（可自动压缩：较旧步骤摘要化，保留最近步骤）。
3. 当前焦点。

规则：

- **共享群聊对话永不自动压缩**：不摘要、不按条数截断、不只给最近几轮。
- **私有过程可自动压缩**：超过该模型窗口时，先把自己的旧步骤压成私有摘要 + 最近步骤；默认用确定性折叠（保留最近步骤，最旧步骤标「已省略」），不额外调用模型；需要语义摘要时可用该成员自己的模型（可选）。源头日志 append-only，用户仍可查看全套。
- 私有过程压到最小后，若「系统 + 人设 + 看板 + 全部共享对话 + 焦点」仍超过窗口 → 该模型 `context_overflow`，**本轮及后续停止参与**；系统事件 + UI 状态提示。其他成员继续。
- 恢复方式只有两种：**用户主动压缩群聊数据**（全群摘要）或**更换更大窗口模型**。自动流程绝不压缩共享对话。
- 1M 与 256K 的区别是**共享对话何时溢出**：256K 更早触发停止，1M 更晚；不是默认只给更少条数。
- 主持人溢出：讨论暂停（主持人无法调度），提示用户压缩群聊数据或更换主持人；不自动用摘要继续。
- 看板是紧凑派生摘要，计入上下文开销；它本身不做运行时压缩。人设正文过大时预检提示，不静默截断。

**用户主动压缩群聊数据（唯一能压缩共享对话的路径）**：

1. 用户点「压缩群聊数据」并确认；默认选一个能装下当前对话的摘要模型（主持人或最大窗口成员，用户可改）。
2. 生成共享摘要，写 `meta.sharedSummary = {text, cutoffGid, createdAt, createdBy:'user', summarizerModel}`；`cutoffGid` 默认回退到最近 1 轮的起点——**最近 1 轮保留全文**（0/1/2 可选），摘要只覆盖更早的消息。
3. 之后所有成员/主持人的请求 = 共享摘要 + `cutoffGid` 之后的全部对话 + 自己的私有过程；原始日志与 UI 全量记录保留。
4. 压缩后重跑预检；此前 `context_overflow` 的成员可在下一轮恢复参与。
5. 自动流程绝不调用这一步。

### 3.12 响应时间：超时、跳过与总时长

不同模型响应时间差异很大，串行讨论最怕一个慢模型拖死全场。运行时为每次发言设置两道计时：

| 计时 | 标准 | 思考模型 | 命中后 |
| --- | --- | --- | --- |
| 首次活动（无 think/chunk） | 45s | 90s | AIStop 本轮、标记超时、跳过 |
| 总时长 | 180s | 240s | 同上 |
| 主持人计划/复盘 | 60s | 240s | 回退轮转 / 用看板生成小结 |
| 整场讨论 | 15min（可配） | 同左 | 暂停并提示用户继续/结束 |

- 超时不是错误：消息标 `timeout`，系统事件写「X 在 N 秒内未发言，已跳过」，讨论继续；主持人下一轮可再请 X。不自动重试超过一次。
- UI 当前发言者显示已用时长、`思考中…` / `正在输入…` / `超时未发言`；用户可手动「跳过当前发言」。
- 首次活动计时把 `ai-think` 也算作活动；思考模型因此有更长的等待窗。
- **主持人也可以思考**：按主持人自身模型的思考能力选择超时档；思考主持会变慢，但不会因此被禁止。UI 显示「主持人正在思考…」。
- `AIStop(roundId)` 取消单个成员；`AIStop(groupId)` 取消全场。
- 讨论总时长与 token/发言数预算同时生效，任一到达即暂停。

### 3.13 两份数据：群聊数据与私有数据（硬规则）

每个成员维护两份数据：

| 数据 | 内容 | 谁能看 |
| --- | --- | --- |
| **群聊数据** | 所有成员最终发送到群聊的对话：正文 + `groupBlock` + 发言人/轮次等对话元数据 | 所有成员、主持人、用户 |
| **私有数据** | 自己的思考链 / reasoning / thinking signature、工具调用与结果、供应商原始过程；按消息 `gid` 关联 | **仅自己与用户**；其他成员与主持人不读 |

规则：

- 私有数据独立存储（`private/<agentId>.jsonl`），**不写进共享群聊日志**；共享日志只有对话。
- 组装某个成员的请求时：自己的历史消息用私有步骤**水合**（thinking / tool calls / tool results + 最终正文）；其他成员的消息只放最终正文 + `groupBlock`。因此每个模型都能看到自己的完整思考与工具过程，但看不到别人的。
- 主持人的私有过程同理：只给用户看，不进成员上下文；主持人也**不读**成员的私有数据。
- `groupBlock` 是成员主动输出的结构化信息，属于群聊数据，共享；它不是内部思考/工具调用。
- 用户可以在消息里展开「仅你可见」的私有过程（思考链 / 工具调用 / 工具结果）；其他成员与主持人没有这个入口，也不会拿到这些内容。
- G5 工具阶段沿用此规则：每个成员的工具循环、工具结果都是私有过程；只把最终结论发到群聊。共享看板/纪要只用群聊数据。
- 私有数据也参与该成员自己的窗口预算；超窗时**只压缩自己的私有过程**；共享对话不压缩，连共享对话都装不下则该模型停止参与（§3.11）。
- 思考 token 计入该成员 usage 与输出预算；`thinkingBudget` 沿用模型条目，不另设全局值。
- 没有思考的模型不显示空思考块；UI 不假设人人都有思考链。
- **主持人也可以思考**：主持人模型可以是思考模型，按自身模型能力选择超时档；UI 明确显示「主持人正在思考…」。思考主持的私有过程同样只给用户看，不进入成员上下文。

### 3.14 并发与账号级限流

- 串行轮（默认）：同一时刻 1 位成员，天然没有同账号并发；慢就是慢，用超时/跳过治理。
- 并行轮：同时最多 `maxConcurrency`（默认 2–3），但**同一账号/API Key 默认只放 1 个**请求（不同账号可并行）——同一 Key 的速率限制通常共享，盲目并发只会 429。
- 主持人与成员不同时发起（计划 → 发言 → 复盘）；避免调度请求和被调度请求互相抢配额。
- 429/网络错误交给现有传输重试；连续失败两次则该成员标记失败并继续，不阻塞其他成员。
- UI 在群设置里显示「共享账号」提示；成员都挂同一账号时建议串行。

### 3.15 串行讨论 vs 并行表态

| | 串行 `sequential`（默认） | 并行 `parallel`（可选） |
| --- | --- | --- |
| 每轮耗时 | 各成员耗时之和 | 最慢成员耗时 |
| 同轮互相回应 | 能（看到前面发言） | 不能（看同一份快照） |
| 讨论质量 | 高，像真实圆桌 | 独立观点收集，像并行问卷 |
| 适用 | 评审、决策、辩论 | 头脑风暴、快速收集、慢模型多 |

- 默认串行；群创建时可选并行，并在 UI 说明「并行轮成员看不到同轮其他人的发言」。
- 并行轮每个成员收到：看板 + 上轮小结 + 与议程相关的最近发言（统一快照）；`replyTo` 指向上轮小结/用户消息，不指向同轮成员。
- 并行轮仍受 token/发言/时长预算；主持人负责合并立场与分歧。
- 不做「边流边接话」的重叠管线：第二位在第一位没说完时发言，会破坏讨论因果，复杂度不值。

> 实施时机：并行轮不在 G3 首发批次内（G4/G5 再评估）；meta 的 `roundMode` 字段自 G1 起按最终 schema 落盘，后补并行不需要迁移。

### 3.16 创建前兼容性预检

纯函数 `preflightGroup(group, agents, config)`，逐成员计算：

- 共享开销：系统 + 人设 + 看板 + **全部共享对话**（有 `sharedSummary` 时用摘要 + cutoff 后对话；不自动压缩）。
- 私有开销：自己的私有过程（按可压缩到的最小步骤估算）。
- 当前焦点。

结果：

- 绿色：≤ 窗口 70%，正常参加。
- 黄色：70–85%，或私有过程需要压缩；可参加，但提示私有过程会被压缩。
- 红色：> 85%，或「系统 + 人设 + 看板 + 全部共享对话」已经塞不下：标记 `context_overflow`，本轮及后续停止参与；用户可**手动压缩群聊数据**、换更大窗口模型、缩短人设或排除。
- 主持人：可以是任意模型，**包括思考模型**；共享对话溢出时暂停讨论，提示压缩群聊数据或换主持人；不自动摘要继续。
- 预检在群创建、成员变更、模型切换、每轮开始、手动压缩后各跑一次；结果作为「开始讨论」按钮旁的兼容性摘要。
- 红色成员不阻塞整群；自动跳过并给系统提示，避免「点了开始才发现某个模型塞不下」。

## 4. 自由模式：保留 v1 的 @ 路由（可选）

自由模式不是默认。用于闲聊/角色扮演/发散，行为：

- 用户消息解析 `@all` / `@A @B` / 无 @（默认接话人）。
- 成员可直接 `@B` 唤醒 B；`@all` 禁止；单条最多 @2 人。
- 硬上限沿用 v1：每回合回复总数、深度、单成员次数、并发、乒乓、token 预算、seenEdges。
- 没有轮次计划、没有看板、没有强制回应；讨论自然结束。
- 用户 `@all` = 每人各回一次，默认不自动接力（可配开启）。

**主持制与自由制的差别**：

| 维度 | 主持制（默认） | 自由制（可选） |
| --- | --- | --- |
| 谁决定下一位 | 主持人 | 消息里的 @ |
| 成员能否直接唤醒别人 | 不能，只能请求 | 能，受上限 |
| 讨论能否持续 | 按轮持续，直到收敛/预算 | 有人 @ 才继续 |
| 风暴风险 | 结构上很低 | 靠上限治理 |
| 适用 | 评审/决策/任务 | 闲聊/角色扮演/发散 |

---

## 5. 防广播风暴：主持制是结构性保证

主持制下：

1. **只有一个调度者**（主持人），成员不能直接触发其他成员；`handoff` 只是请求。
2. **同一时刻只有一位成员发言**（默认串行；可配 2 并发，但不推荐——讨论需要听到彼此）。
3. **每轮每人最多一次实质发言**；主持人跳过无话可说的人。
4. **轮数、发言数、token、时长全部有硬上限**；到限即停并给提示。
5. 主持人不能指定非成员/静音/失效模型；运行时二次校验。
6. 失败重试：每成员每轮最多一次；连续两次主持人解析失败则暂停。

自由制下保留 v1 全套上限（见 §12），但它是 opt-in，不承担「持续讨论」的主路径。

因此，「能持续讨论」和「不出现广播风暴」不再矛盾：**持续的是轮次，受限的是调度权与预算**。

## 6. 数据模型

### 6.1 智能体（`ai-config.json` 新增 `agents[]`）

```json
{
  "id": "agent-m5x2-a1b",
  "name": "审查员",
  "color": "violet",
  "role": "代码审查与风险检查",
  "modelRef": "profile-1|model-2",
  "personaText": "你是……",
  "replyStyle": "professional",
  "temperature": null,
  "slowTier": false,
  "chair": false,
  "enabled": true,
  "createdAt": 1760000000000,
  "updatedAt": 1760000000000
}
```

- `id`：`aiNowId('agent-')`，自动唯一，不随改名变化。
- `name`：1–32 字符；无空白与 `@`；全局唯一（NFC + 小写比较）；保留词 `all / everyone / 全体成员 / 所有人` 禁用。
- `modelRef`：`账号id|模型id`，复用 `resolveModelRef`；同一账号/模型可被多个智能体引用；失效时显示「模型不可用」，不静默回退。
- `chair: true`：可在群设置里被选为主持人；主持人只做调度与纪要，不参与辩论。
- `color`：固定调色板；用于头像圆点与消息标识。
- `role`：一句话职责，进入成员名单与主持人参考。
- `personaText`：≤4096，复用 `PERSONA_GUARD_DATA` + XML 转义。
- `replyStyle`：复用 `REPLY_STYLES`。
- `temperature`：`null` = 跟随账号。
- `slowTier`：超时按思考/慢速档计算（兼容端点不暴露 reasoning 能力时手动标注；预检徽标同步采用）。
- 上限 32 个智能体；删除不级联，群内显示「已删除成员」。

- `mode`：`roundtable` / `task` / `free`；辩视为 `roundtable` + 角色模板。
- `chair.kind`：`ai` / `member` / `user`；`policy`：`round-plan` / `adaptive`。

- `discussion`：讨论看板（§3.2）；每轮复盘更新。
- `minutes`：最终纪要（结构化 + 可选润色文本）。
- `memberIds` 只存引用；消息里存发送时的名字/颜色/模型快照，改名/删人后历史仍可读。

### 6.3 群消息（`session.v1.jsonl`）

事件沿用 `header / msg / meta / archive / reset`；消息字段：

```json
{
  "gid": "gm-m5x2-e4f",
  "role": "assistant",
  "agentId": "agent-a",
  "agentName": "架构师",
  "agentColor": "blue",
  "model": "deepseek-v3",
  "content": "……",
  "ts": 1760000000000,
  "turnId": "turn-m5x2-1",
  "round": 1,
  "replyTo": "gm-...",
  "addressedTo": ["agent-b"],
  "stance": "disagree",
  "groupBlock": {"stance": "disagree", "keyPoints": [], "handoff": ["agent-b"]},
  "usage": {"input": 1200, "output": 340},
  "hasPrivate": true,
  "timing": {"startedAt": 0, "firstActivityAt": 0, "finishedAt": 0, "ttftMs": 0, "totalMs": 0},
  "timeout": false,
  "status": "done"
}
```

- `round`：第几轮；讨论看板/纪要/UI 分组使用。
- `replyTo`：被回应的消息 gid；主持人焦点可指定。
- `stance`：结构化立场；正文里可读。
- `hasPrivate`：该消息在 `private/<agentId>.jsonl` 里是否有私有过程；共享日志本身**不含**思考链/工具调用。
- `timing`：TTFT / 总时长，用于速度徽标、预计耗时与超时诊断；只在 UI 使用，不进其他成员上下文。
- `timeout`：超时跳过标记；不是错误，讨论继续。
- 系统事件（轮次开始/结束、主持人小结、到限、成员失效）用 `role:"system"` + `kind:"group-event"`，不进模型上下文。
- 流式期间只存内存；完成/失败/停止时 append 完整消息（v1 牺牲崩溃时的半截回复；G5 可加周期快照）。
- 主持人消息作为 `role:"assistant"` + `agentId: chair` / `chair: true`，UI 样式与成员区分；正文是主持人小结，不是辩论发言。

### 6.4 私有过程日志（每个模型自己的数据）

`private/<agentId>.jsonl`，按消息 `gid` 存该成员自己的完整执行步骤：

```json
{
  "gid": "gm-m5x2-e4f",
  "agentId": "agent-a",
  "steps": [
    {"kind": "thinking", "text": "……"},
    {"kind": "assistant_tool_calls", "content": "", "toolCalls": [{"id": "call_1", "name": "read_file", "arguments": "{}"}]},
    {"kind": "tool_result", "toolCallId": "call_1", "name": "read_file", "content": "……"},
    {"kind": "thinking", "text": "……"}
  ],
  "ts": 1760000000000
}
```

- **只由该成员自己的请求读取/水合**；其他成员和主持人不读。v1 无工具时 `steps` 通常只有 `thinking`；G5 工具阶段扩展。
- 私有日志 append-only，**保留全套**；请求超窗时只压缩自己的私有过程（旧步骤摘要化），**绝不压缩共享对话**，也不删源头。用户仍可在 UI 查看完整私有过程。
- 最终可见正文以共享日志里的消息为准；私有日志只存通往该正文的过程，避免两处正文不一致。
- 主持人的私有过程也写自己的 `private/<chairAgentId>.jsonl`。
- 用户 UI 可展开「仅你可见」查看这些步骤；共享看板/纪要/其他成员上下文都不读。
- 私有日志会随讨论增长；请求上下文压缩**不删源日志**；用户可在存储清理里删整群时一并删除。

### 6.5 存储位置

```
%APPDATA%\CandySweet\CaDt-DataLens\ai-groups\<group-id>\
  meta.json
  session.v1.jsonl          # 共享群聊对话（只有对话）
  private\<agentId>.jsonl   # 每个模型自己的思考/工具过程（仅自己与用户可读）
```

- 复用 `internal/sessionstore` 的 `Store`（Root 换成 `ai-groups`）：原子 append、跨进程锁、meta 原子替换、回收站删除、torn tail 修复全部继承。
- 与普通会话根目录分离，原因：
  - 「清空所有 AI 会话」不会误删群聊；
  - 群聊不混进会话列表、会话搜索索引、会话投递目标；
  - 群聊生命周期独立治理。
- 代价：群聊默认不参与全局会话搜索（G5 再评估独立索引）；存储清理需新增 `ai-groups` 条目。

## 7. 上下文组装

### 7.1 成员请求：群聊数据全量 + 自己的私有数据

```
[system]
  <group_rules>      你在多智能体圆桌中；只回应被要求的内容；引用具体发言人；
                     不要复述已达成共识；不要假装执行了未提供的工具；禁止 @全体成员
  <participants>     用户 + 其他成员名字/职责（不含别人的人设正文）
  <agent_identity>   你是 <name>；<role>
  <agent_persona>    人设正文（PERSONA_GUARD_DATA + XML 转义）
  <reply_style>      可选
  <discussion_mode>  roundtable / task；当前第 N 轮；目标（explore/decide/...）
  <discussion_board> 议程、已达成共识、未决分歧、未决问题、任务（派生摘要，辅助对齐）
  <chair_focus>      主持人给本条发言的焦点（回应谁、解决什么）
  <output_language>  全局输出语言规则（抽成纯函数，与主面板同源）
[shared dialogue]
  全部群聊消息，按时间顺序：
  - 用户消息：user（[用户] 前缀）
  - 其他成员消息：user（[名字] 前缀；只含最终正文 + groupBlock）
  - 自己的消息：assistant，用 private/<agentId>.jsonl 里的步骤水合
    （thinking / tool calls / tool results + 最终正文）
[尾巴]
  本轮轮到你（<name>）发言；请回应焦点；如无新信息可明确说「无补充」并给 stance
```

- **默认全量**：不按条数截断，也不拿看板替代对话；看板只是派生摘要，帮助对齐。
- 如果群有 `sharedSummary`（用户手动压缩过），共享对话部分 = 摘要 + `cutoffGid` 之后的全部消息；未压缩时就是全部消息。原始日志始终保留。
- 自己的私有过程只进自己的请求；其他成员和主持人只看到群聊数据。
- 自己的历史消息**水合**私有步骤：v1 是 thinking；G5 是 thinking + tool calls/results。提供商支持原生 thinking 回放时用原生字段，不支持时用私有历史块；两种都只对本人可见。
- 共享对话不带模型名、账号、usage、耗时等元数据；这些只在用户 UI 展示，避免成员按“对方是什么模型”而不是按观点回应。
- 连续同角色消息合并；永远以 `user` 结束；不使用预填充。
- 成员看不到别人的人设正文、模型配置、API Key、私有过程；只看到名字/职责/群聊发言。
- 请求预算按该成员的 `contextWindow - outputWindow - reserve` 计算；私有过程超窗时自动压缩；共享对话不压缩，连共享对话都装不下则该成员停止参与（§3.11）。
- 输出预算按该成员的 `outputWindow` 与思考配置预留；不设一个会压掉思考预算的全局 `max_tokens`。

### 7.2 主持人请求：群聊数据全量 + 主持人自己的私有数据

```
[system]
  你是这场圆桌的主持人，不参与辩论；你的目标是让讨论覆盖议程并收敛。
  成员名单/职责、议程、看板、预算（第 N/max 轮、已发言数/上限、token 预算）
[shared dialogue]
  全部群聊对话（默认全量；有 sharedSummary 时 = 摘要 + cutoff 后对话；不自动压缩；主持人溢出则暂停）
[private chair history]
  主持人自己的思考/调度过程（只有主持人自己与用户可见）
[instruction]
  输出严格 JSON：chairMessage / plan / statePatch / roundComplete / done / minutes
```

- 主持人同样**不读成员私有数据**；只能看群聊数据。
- 主持人**可以是任意模型，包括思考模型**；自己的思考过程只给用户看，并在自己的后续调用中水合。思考主持会变慢，UI 显示「主持人正在思考…」，超时按主持人的思考档放宽。
- 默认给主持人全部群聊对话；`round-plan` 仍是一次计划 + 一次复盘，不因为上下文全量就变成每句一调。
- 轮末复盘看本轮全部发言；如果主持人的共享对话溢出窗口，暂停讨论并提示用户压缩群聊数据或更换主持人；**不自动压缩共享对话**。
- 主持人输出解析失败时回退，不让整个讨论崩掉。

### 7.3 窗口与压缩

- **共享对话永不自动压缩**：全量装入。若某模型的「系统 + 人设 + 看板 + 全部共享对话」超过窗口，即使私有过程压到最小，该模型 `context_overflow`，停止参与。
- **私有过程可自动压缩**：先摘要自己的旧步骤，保留最近步骤；源头日志不删，用户仍可查看全套。
- **用户主动「压缩群聊数据」**：生成共享摘要 + `cutoffGid`，之后所有请求用摘要 + cutoff 之后的对话；原始日志与 UI 全量记录保留；压缩后重跑预检。
- **主持人共享对话溢出**：暂停讨论，提示压缩群聊数据/换主持人/换成员模型；不自动摘要继续。
- 1M 与 256K 的差异是共享对话何时溢出；不设固定条数上限。

  - 系统事件：细条提示；
  - 流式：当前发言者先出现 typing 行；增量 80ms 节流，不整屏重建。

  - textarea + @ 补全（成员/全体成员）；发送/停止；
  - 在讨论进行中发送：默认作为「用户插话」在下一轮计划生效；可点停止立即中断；

  - 说明：**只压缩共享群聊对话**，生成摘要 + 截止消息；原始记录仍保留、UI 仍可看全量；所有成员后续从摘要继续。
  - 选择摘要模型（默认能装下当前对话的主持人/最大窗口成员，可换任意模型，装不下红色警示）；保留最近 1 轮全文（0/1/2 可选）；预计 token 与调用量。

- 验收：创建 3 个智能体（同账号不同模型、不同账号同模型均可）；重启保留；重名被拒绝；删模型后显示不可用。

### G1 — 群聊存储、列表与创建

- `groupstore_app.go` + bindings + 存储清理 + mock；`ai-group-store.js` + 测试；侧栏群聊列表（带标题过滤）；新建群聊（议题/目标/模式/主持人/轮数/预算/超时；轮次执行仅串行，`roundMode` 字段按最终 schema 落盘；无主持人智能体时「一键创建默认主持人」）；兼容性预检；群标签页空壳；群设置。
- 验收：创建圆桌群并重启恢复；主持人/成员/轮数/超时/轮次执行保存；删除进回收站并关标签页；预计调用量与兼容性红黄绿显示正确。

### G2 — 单成员生成与流式

- `ai-group-runtime.js` 单发言路径：按成员模型窗口组装请求（§3.11）、`AISendChat`、流式、TTFT/总时长、完成/错误/超时/停止、落盘；视图消息区/输入区/Markdown/停止。
- 验收：用户开始讨论 → 主持人开场 → 指定成员流式发言；成员默认拿到全部群聊对话 + 自己的私有过程；私有过程超窗时只压缩自己，共享对话不压缩；共享对话溢出则该成员停止参与；Markdown 正常；停止有效；重启 transcript 与私有日志都能恢复。

### G3 — 主持讨论循环（核心）

- `ai-group-chair.js`：计划/复盘/纪要契约、回退、预算；轮次循环；看板合并；收敛判定；用户点名/@all/暂停/继续/结束；主持人消息与可见性；用户主持（下一位选择器 + 焦点输入，AI 主持人暂停调用）。
- 上下文门禁（§3.11）：共享对话溢出 → `context_overflow` 停止该模型；私有过程自动压缩；用户手动压缩群聊数据 + 截断点 + 重新预检/恢复；主持人溢出暂停。
- 验收（假模型/真模型各一轮）：
  1. 4 位成员 × 2 轮 → 每人每轮最多一次，总发言 ≤ 8；主持人计划/复盘调用数符合策略；
  2. 第 1 轮后主持人判定收敛 → 不再开第 2 轮；
  3. 用户 `@B` → 下一轮计划必须包含 B；B 不可用时提示且不崩；
  4. 用户 `@全体成员` → 下一轮所有可用成员各一次；
  5. 成员 A 的 `handoff: ["B"]` 在主持制下只作为请求，主持人不采纳则不直接唤醒 B；
  6. 主持人 JSON 非法 → 回退轮转且讨论继续；连续两次失败 → 暂停提示；
  7. 达到轮数/发言数/token 上限 → 停止并给提示；
  8. 暂停/继续/结束并总结 → 状态与纪要正确；
  9. 同一成员同一轮不会因为多人 @ 而重复发言；
  10. 自由模式下 v1 的 @ 风暴上限仍然有效；
  11. 成员窗口不足 → 预检红色并被跳过，讨论继续；
  12. 串行轮中某成员超时 → 标记超时、继续下一位，不阻塞整轮；
  13. 同账号并行 → 账号级并发不超过 1，不出现同 Key 并发风暴；
  14. 思考模型 → 思考只给用户看；本成员自己的后续请求水合自己的私有过程，其他成员/主持人/看板/纪要绝不出现；工具调用/结果同理（G5）；
  15. 1M / 256K 成员默认都拿**全部群聊对话**；共享对话永不自动压缩，不按固定条数截断；
  16. 共享 JSONL 只有群聊对话，不含思考/工具字段；私有日志按 agentId 分开；A 的请求含 A 的私有过程，不含 B 的；
  17. 删除群时私有日志随群目录一起删除；
  18. 共享对话溢出 256K 成员但 1M 成员仍装得下 → 256K 成员 `context_overflow` 被跳过，1M 继续；不产生自动共享摘要；
  19. 私有过程很大但共享对话装得下 → 只压缩该成员的私有过程，成员继续；共享对话原样全员可见；
  20. 用户手动压缩群聊数据 → 生成共享摘要 + cutoff；原始日志与 UI 全量保留；之前溢出的成员在下一轮可恢复；
  21. 主持人共享对话溢出 → 讨论暂停，不自动摘要；提示压缩群聊数据或换主持人。

### G4 — 任务模式、辩论预设、纪要与导出

### 11.2 手工验收

- 4 个智能体（不同模型/人设）+ AI 独立主持人，跑一个真实议题（如「这个功能该不该拆成独立存储」），检查：是否多轮、是否互相回应、是否收敛、纪要是否可用；
- 用户中途插话/点名/@all/暂停/继续/结束；
- 成员模型失效/删除/静音；主持人模型失效；主持人返回坏 JSON；
- 故意混用 1M / 256K / 小于 256K 的成员：默认都全量；共享对话溢出时 256K 更早停止参与、1M 继续；私有过程分别压缩；用户手动压缩群聊数据后溢出的成员可恢复；
- 慢模型（或思考模型）与普通模型混排：超时跳过、下一轮可再请、整场不无限等待；
- 同账号两个成员在并行轮：账号级并发不超过 1；
- 关闭/重开标签页；重启；两个群同时讨论；长讨论触发窗口裁剪；
- 深色/浅色、窄窗口、悬浮窗口（群聊入口隐藏并提示主窗口使用）。

## 13. 成本、性能与体积

- 不新增 npm / Go 依赖；复用 `sessionstore` 与现有传输层。新增前端代码估算 5–7k 行（含测试），主包增量约 70–120 KB（压缩前），无 vendor。
- 成本是主要成本：
  - `round-plan`：4 成员 × 2 轮 ≈ 8 次成员调用 + 4 次主持人调用 + 1 次纪要 ≈ 13 次；
  - `adaptive`：约 17–20 次；
  - 任务模式再加任务相关发言；
  - **全量上下文**：每次发言都带全部群聊对话 + 自己的私有过程，输入 token 随讨论长度增长；1M 模型单次比 256K 更贵；UI 显示累计，默认不设总上限，可手设安全阀；
  - 共享对话不自动压缩：256K 模型会更早 `context_overflow` 停止参与，用户需手动压缩群聊数据或换模型；这只是门禁，不额外调用模型；
  - 创建群聊显示预计调用量；讨论进行中显示已用调用/token；到预算即停。
- 时延：
  - 串行轮耗时 = 各成员耗时之和；并行轮 ≈ 最慢成员；
  - 思考模型通常更慢；主持人也可以思考，按自身思考档放宽超时；超时/跳过避免无限等待；
  - 同账号多成员共享速率限制；并行轮按账号限流（同账号默认 1 并发）；
  - 群创建显示预计耗时（有历史测速用历史，否则用默认假设）。
- 性能：
  - 串行发言（默认）降低并发压力；主持人计划一次排一轮，减少等待；
  - 消息按 gid 增量更新，流式 80ms 节流；
  - 群列表只读 meta；transcript 按需加载；
  - 默认每轮带全部群聊对话（作者要求完整上下文），输入 token 会随讨论增长；共享对话不自动压缩，私有过程可压缩；共享溢出该模型停止，用户可手动压缩群聊数据；UI 显示累计用量。
- 存储：共享对话与每个成员的私有过程分开追加（`session.v1.jsonl` + `private/<agentId>.jsonl`）；meta debounce；任务板/纪要即时落盘；存储清理新增群聊目录。私有过程可能很大，UI 显示各文件大小，删除群时一并清理。

## 14. 风险与边界

| 风险 | 处理 |
| --- | --- |
| 主持人质量不稳/偏袒 | 默认独立主持人（不参与辩论）；JSON 契约 + 回退轮转；用户可切换人工主持；主持人消息可见 |
| 主持人调用成本 | `round-plan` 一轮两次；可换便宜模型；用户主持零成本；预算硬上限 |
| 慢模型拖死串行轮 | 首次活动/总时长双计时；超时标记并跳过；用户可手动跳过；可切并行轮；测速与预计耗时 |
| 小窗口模型塞不下 | 共享对话不自动压缩；256K 更早遇到溢出并停止该模型；私有过程可自动压缩；用户可手动压缩群聊数据或换大窗口模型 |
| 共享对话溢出某个成员 | 该模型 `context_overflow` 停止参与，其他成员继续；UI 明示原因与「压缩群聊数据/换模型」入口；不自动摘要 |
| 主持人共享对话溢出 | 讨论暂停；提示压缩群聊数据或换主持人；不让主持人用自动摘要继续 |
| 手动压缩误操作 | 只压缩共享对话视图，生成摘要 + cutoff；原始日志与 UI 全量保留；压缩前确认，压缩后可回看 |
| 思考链泄漏/膨胀 | 思考写在该成员的私有日志，只给本人与用户；其他成员/主持人/看板/纪要不读；本人请求可水合自己的私有过程 |
| 同账号并发 429 | 并行轮按账号限流（同账号默认 1）；串行轮天然无并发；连续失败标记后继续 |
| 模型能力差异导致质量不均 | 成员徽标与预检；主持人用焦点补齐上下文；用户可换模型/排除小窗口成员 |
| 成员不互相回应 | 主持人给焦点（“回应 A 的反对意见”）；看板注入；提示词强制引用；无新信息要明确说“无补充” |
| 讨论跑题 | 议程 + `agendaItem` + 主持人复盘；用户可暂停纠偏 |
| 讨论不收敛 | 轮数硬上限 + 收敛判定 + 用户结束；纪要记录未决问题，不强行假装达成共识 |
| 广播风暴 | 主持制单调度者/单发言者；自由制全套上限；@all 只排一轮 |
| 上下文膨胀 | 共享对话默认全量且不自动压缩，溢出即停该模型；私有过程自动压缩；用户手动压缩群聊数据；UI 显示累计 token；默认不设总上限，可手设安全阀 |
| 提示注入/成员互相操纵 | 他人消息按用户数据/观点处理；人设护栏；无工具时无文件内容注入面 |
| 模型/账号被删 | 成员显示不可用，跳过并提示；不静默换模型 |
| 多窗口同群并发 | v1 已知限制；后续群级活动锁/单写者 |
| 关闭标签页后讨论继续 | 刻意设计；群列表显示运行态；重开恢复 |
| 崩溃时半截回复 | v1 只存完成消息；重启该轮缺失，不产生坏日志；G5 可加周期快照 |
| `ai-panel.js` 膨胀 | 群聊全部落新模块，面板只加配置归一化与薄 API；视图走内容区标签页 |
| 与 side-chat-tab 争内容区 | 两者都是虚拟文档；统一 `format.id` / `createDocEditor` 分支；标签上限分别计算 |

## 15. 推荐默认值（可直接按此开工）

| 决策 | 推荐默认 | 理由 |
| --- | --- | --- |
| 群聊首要用途 | **AI 圆桌讨论（多轮、产出纪要）** | 直接回答「不同 AI 互相讨论」；任务/自由作为预设 |
| 默认调度 | **AI 独立主持人 + `round-plan`** | 单调度者防风暴；一轮两次主持调用，成本可控；主持人不参与辩论 |
| 主持人来源 | 无主持人智能体时「一键创建默认主持人」（内置人设写进 `agents[]`，可编辑） | 用户不必手写主持人提示词；数据模型单一路径 |
| 默认轮数 | **2 轮** | 足够互相回应与收敛；1 轮适合轻量，3 轮适合深度 |
| 默认成员数 | 3–4 人（上限 8） | 讨论质量与成本的平衡 |
| 默认预算 | 12 次成员发言 / 2 轮；总 token 默认不限（可手设安全阀） | 全量上下文会推高用量；用发言数/轮数控制调用，UI 显示累计，用户可自设预算 |
| 轮次执行 | **串行 `sequential`**（并行表态可选，G4/G5 再评估） | 串行才能同轮互相回应；慢模型用超时治理，不为速度牺牲讨论质量 |
| 超时 | 首次活动 45s（思考 90s）；总时长 180s（思考 240s）；主持人 60s（思考 240s）；整场 15min；另设标准/宽松预设 | 慢模型不拖死全场；超时跳过而非报错；非思考 180s 覆盖全量上下文变长后的 TTFT；思考主持与成员思考档对齐 |
| 默认上下文 | **全部群聊对话 + 自己的全部私有过程**；共享对话不自动压缩，私有过程可自动压缩 | 作者要求默认全量、不按 8–12 条截断；共享溢出时该模型停止，等用户手动压缩 |
| 上下文预算档 | 1M / 256K / <256K 兜底（标黄） | 1M 更晚遇到共享对话溢出，256K 更早；不是固定条数 |
| 共享对话溢出 | **该模型停止参与**；其他成员继续；UI 给「压缩群聊数据/换模型」 | 不自动压缩共享对话；主持人溢出则暂停讨论 |
| 手动压缩群聊数据 | 用户触发；摘要 + cutoff，默认保留最近 1 轮全文（0/1/2 可选）；原始日志与 UI 全量保留；压缩后重跑预检，溢出成员可恢复 | 唯一能压缩共享对话的路径；自动流程不碰；最近轮逐字保留减少摘要失真 |
| 私有数据留存 | **按群独立保存** `private/<agentId>.jsonl` | 作者确认：A 群的私有过程不带到 B 群；群删除时一并删除 |
| 主持人模型 | **任意可用模型，含思考模型** | 作者确认主持人可以思考；思考主持按思考档超时，UI 显示延迟提示 |
| 账号并发 | 并行轮同账号默认 1 | 同 API Key 共享速率限制，避免 429 |
| 兼容端点能力标注 | 智能体布尔 `slowTier`（超时按思考/慢速档） | 兼容端点不暴露 reasoning 时手动标注，避免思考模型被误跳过 |
| 双数据 | 群聊数据 = 只有对话；私有数据 = 自己的思考/工具全过程；只给本人与用户 | 自己的请求水合自己的私有过程，其他成员/主持人不读 |
| 思考链 | 只在该消息的私有过程折叠展示；本人可见、用户可见 | 保护思维链、控制共享上下文、避免跨模型泄漏 |
| 无 @ 行为 | 主持人按议程安排，不再「只回一句」 | 这是本次修订的核心 |
| 用户 @A | 主持人下一次计划必须包含 A | 用户点名优先级最高 |
| 用户 @all | 下一轮所有可用成员各一次 | 不是「各回一句就结束」 |
| 成员 handoff | 主持制下是请求；自由制下才是直接接力 | 防风暴与讨论自然度的平衡 |
| 成果 | 结构化纪要 + 可选任务板 | 群聊要有用，不只是聊天记录 |
| 承载面 | **内容区标签页** | 看板 + 多成员消息需要宽度；已有 sideChat 先例 |
| 群聊存储 | **独立 `ai-groups` 根** | 避免清空会话误删、避免混入会话搜索/投递 |
| v1 工具 | **不给工具**；G5 只读再评估 | 并发写文件不可控；先验证讨论质量 |
| 自由模式 | **opt-in，G5 实施**（@ 解析器 G3 已就绪） | 保留闲聊/角色扮演，但默认不承担主路径；接力引擎与圆桌循环正交，后置不浪费工作 |
| 智能体数量 / 群成员 | 32 / 8 | UI 与上下文可控 |
| 名字约束 | 1–32 字符，无空白/`@`，全局唯一（NFC+大小写） | 点名解析确定性；输入框补全自动加尾随空格 |

## 16. 开放问题（已确认，2026-11-17 与作者收口）

| # | 问题 | 结论 |
| --- | --- | --- |
| 1 | 首要用途 | **圆桌讨论**为主场景；任务/自由是同一引擎的预设 |
| 2 | 默认主持人 | **AI 独立主持人**；创建群聊时若无主持人智能体，提供「一键创建默认主持人」（内置人设模板写进 `agents[]`，用户可编辑，数据模型单一路径） |
| 3 | 默认轮数 | **2 轮**（1–3 可配）；不做「开放收敛档」——深度档 3 轮 + 主持人每轮可判停已近似覆盖，实测收敛判定可靠后再评估自动档 |
| 4 | 强制发言 | **不强制**；主持人可跳过并看板标注；同一成员连续两轮无发言时 UI 提示（可点名或移除），不静默 |
| 5 | 自由模式 | **后置 G5**；@ 解析器 G3 照做（用户点名复用），只推迟 @ 接力引擎 |
| 6 | 任务板 | **G4**；G3 结束时看板 `actionItems` 已够「带目标的圆桌」用 |
| 7 | 用户主持 | **随 G3 交付**（下一位选择器 + 焦点输入）；兼作调试期的确定性调度与主持人失效的人工兜底 |
| 8 | 全局搜索 | v1 **不进**；群列表标题前端内存过滤；G5 再评估独立索引，不动 `sessionindex` |
| 9 | 并行模式 | **G3 不做**（G4/G5 再评估）；meta `roundMode` 字段自 G1 按最终 schema 落盘，后补不迁移 |
| 10 | 超时 | 两档 + 标准/宽松预设，**不做按成员覆盖**；非思考总时长 **120s → 180s**（全量上下文推高 TTFT，跳过的代价是整次重请求） |
| 11 | 思考主持 | 总时长对齐成员思考档 **240s**（新增 `chairThinkingMs`）；标准档维持 60s |
| 12 | 手动标注 | 智能体级布尔 **`slowTier`**（按思考/慢速档超时，覆盖自动推导；预检徽标同步），单开关不搞双矩阵 |
| 13 | 摘要模型 | 默认推荐（主持人/最大窗口成员）+ 下拉任意可换 + 装不下红色警示；「用户粘贴摘要」**G4 补**（所有模型装不下时的兜底） |
| 14 | 保留轮全文 | **默认保留最近 1 轮全文**（cutoff 回退到其起点），压缩弹窗可选 0/1/2；实现近零成本，显著减少摘要失真 |
