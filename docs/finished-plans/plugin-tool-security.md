# 插件 AI 工具注册：安全模型设计（M2）

> 状态：**已定稿并被 M3 采纳**（2026-11-19 评审通过；`cadt.registerTool` 全链路已在 M3 落地，2026-11-21 随路线图归档移入 `finished-plans/`）。这是 `docs/finished-plans/plugin-extension-roadmap.md` 里 **M2** 的产出：`cadt.registerTool`（M3）动代码**之前**必须先定稿的那份安全模型。

## 1. 目的与范围

**要解决的问题**：插件目前无法给 AI 加能力。`AI_TOOL_DEFS` 是静态字面量表，`toolsForScope()` 内部是硬编码列表，插件注册的工具无处落地。

**本文只定安全模型**，不定 API 形状的细节；API 草案见路线图 2.1 节。本文回答四个问题：谁能用、怎么授权、怎么审批、防得住什么防不住什么。

**核心结论（一句话）**：插件工具不是新物种，它是 **MCP 工具的同构延伸**——同样「外部来源、能力未知、有副作用」，因此**复用 MCP 那套已验证的安全模型**，不发明第二套。

## 2. 现状依据：MCP 先例

MCP 工具是仓内唯一「外部来源的工具」先例，其模型已落地并经真实使用检验。插件工具逐条对齐：

| 机制 | MCP 现状（证据） | 插件工具应对齐为 |
| --- | --- | --- |
| **下发条件** | `ctx.mcpToolDefs && AI_WRITE_SCOPES.includes(scope) && !planMode`（`frontend/src/ai/ai-tool-defs.js:1137`）——读档不给、计划模式不给 | 同条件 |
| **全局开关** | `mcpToolDefs()` 首行 `if (!enabled) return []`（`frontend/src/ai/ai-mcp.js:65`） | 加同形全局开关 |
| **命名与路由** | 公开名 `mcp__<server>__<tool>`；`executeTool` 里 `if (name.startsWith('mcp__')) return executeMcpTool(...)`（`frontend/src/ai/ai-panel.js:8773`），不进静态 switch | `plugin__<pluginId>__<tool>`，独立路由分支 |
| **计划模式拒绝** | `PLAN_MODE_DENIED_TOOLS.has(name) \|\| name.startsWith('mcp__')` → 直接拒（`ai-panel.js:8765`） | 同拒绝 |
| **审批** | 统一走 `invokeMcpToolWithApproval`（`ai-panel.js:8212`），返回 `{ok, denied, message}` 区分「用户拒绝」与「调用失败」 | 同一条链 |
| **按工具授权** | MCP 服务器级 `enabledTools` 勾选；`ai-mcp-config.js` 把 `enabledTools` 列为**红线**（AI 代配时不得修改） | 插件级逐工具授权，同样列为红线 |
| **dangerous 短路** | `if (dangerous && scope !== 'full') return {decision:'ask', source:'dangerous', singleUse:true}`（`frontend/src/ai/ai-permissions.js:254`） | **插件工具永远不许标记 dangerous** |

`AI_SCOPES = ['read','edit','auto','full']`，`AI_WRITE_SCOPES = ['edit','auto','full']`（`frontend/src/ai/ai-constants.js:30-31`）。

## 3. 威胁模型

### 3.1 防得住什么

| 威胁 | 防护 |
| --- | --- |
| **未知能力被静默启用** | 默认关闭；插件装了不授权，模型连工具定义都看不见（不下发即不可见，不是只在执行时拒绝） |
| **模型自行决定调用敏感操作** | 全部走审批链，用户逐次可见（或按既有规则批量放行），无 dangerous 捷径 |
| **只读档被外部副作用污染** | 普通工具在只读档不下发；声明 `readOnly` 的工具需用户显式开启「只读档可用」才下发（D1） |
| **计划阶段偷跑副作用** | 计划模式直接拒绝，与 MCP 一致 |
| **上下文被塞爆** | 数量与体积上限（见 §6），超限拒绝注册而非静默截断 |
| **用户不知情** | 来源标记贯穿工具卡 / 审批卡 / 工具目录 |
| **绕过审批的越权组合** | 插件工具**不代理**内置写工具（`write_file` / `edit_file` / `run_command`），断掉「插件工具 → 内置写能力」的组合链 |

### 3.2 防不住什么（**必须向用户明示**）

> **审批只约束「AI 触发插件工具」这一条路径，约束不了插件代码自己干活。**

插件代码在 WebView 主文档里以 `new Function('cadt', code)` 执行，拥有与应用相同的权限：完整 DOM、`cadt.runCommand` / `runCommandSync`（可起任意进程）、`cadt.openPath`、读写本机文件。插件**不需要**任何 AI 工具授权就能自己执行命令——它在加载那一刻就有这个能力。

这与 `docs/reports/incident-2026-11-18-workspace-wipe.md` 记录的「脚本内 shell 绕过规则层」是**同一类结构性盲区**：规则层只能约束经由它的调用，约束不了已经在其下游运行的代码。

因此：
- 文档与 UI 里**不得**出现「插件工具已受审批保护，所以插件是安全的」这类暗示。
- 真正的防线是「只安装可信来源的插件」——这与现有信任模型一致（`docs/plugins/README.md` 已声明插件与应用同权限）。
- 插件工具授权的作用是**限制 AI 的能力面**（少一个被提示注入操纵的入口），不是**限制插件的能力面**。

### 3.3 声明的落点（本版决策：安装确认框）

完整声明写在**安装插件的确认框**里（本就不存在、需新增或复用现有确认框），措辞：

> 插件代码与您手动运行脚本的权限相同（可读写本机文件、执行命令）。
> 下面授权的「插件工具」只影响 AI 能否调用它，**不会限制插件本身的能力**。

**覆盖缺口与补丁**（实施时必须处理，否则声明会落空）：安装确认框只在「从仓库地址 / 插件市场安装」路径出现；「添加插件文件夹」「导入 .zip」「切换插件目录模式」都没有确认框——这些路径进来的插件看不到声明。

补丁：在授权区分组标题旁挂一个 `data-tip` 气泡（**不占版面**，悬停 / 聚焦即显示），内容同上精简为一句。这样既守住「别在设置页写长段落」的意图，也不留死角。

## 4. 设计决策

### D1 下发条件（两条路径）

```
注入条件 =
    全局开关开启
 && 该插件已允许 && 该工具已允许
 && !planMode
 && ( 普通工具：scope ∈ {edit, auto, full}
    | 只读工具：scope 任意，且该工具的「允许在只读档使用」已由用户显式开启 )
```

不在条件内时**不下发定义**（模型看不见），而不是「下发但执行时拒绝」——后者会浪费上下文并诱导模型反复尝试。

**只读工具的「声明」与「授权」是两回事**（本版决策：允许插件声明只读工具，但声明不等于放行）：

| 环节 | 谁决定 | 语义 |
| --- | --- | --- |
| 插件声明 `readOnly: true` | 插件作者 | 「我自认为这个工具无副作用」——**仅是候选资格** |
| 工具级「允许在只读档使用」 | **用户显式勾选**（默认关） | 真正放行 |

理由：插件自我声明不可信。让它单方面声明就能在只读档生效，等于插件给自己发通行证；加上用户显式勾选就是双人复核——作者声明意图，用户确认授权。

**`readOnly` 只影响下发，不影响审批**：只读档里下发的插件工具执行时仍走 D4 的审批链（「只读」是插件的说法，不是系统的保证）。

### D2 命名空间与路由

- 公开名：`plugin__<pluginId>__<toolName>`
- 校验：`pluginId` / `toolName` 各限 `[a-z0-9_]`，总长 ≤ 64（与既有工具名规则对齐）
- 路由：在 `executeTool` 开头、静态 switch 之前加
  ```js
  if (name.startsWith('plugin__')) return executePluginTool(name, input, ctx);
  ```
- 理由：与 `mcp__` 同构，零侵入既有分支；也便于在日志 / 审计里一眼识别来源。

### D3 授权模型：全局开关 + 逐插件逐工具

三层，缺一不可：

1. **全局总闸**（默认关）：设置 → AI → 权限 → 插件工具 的总闸；关掉后所有插件工具不下发。**只有用户能打开**（见下方约束 3）。
2. **插件级允许**（默认关）：插件行上的「允许此插件向 AI 提供工具」。
3. **工具级允许**（默认关）：列出该插件注册的每个工具（名字 + 描述首行），逐个开关；声明了 `readOnly` 的工具多一个「允许在只读档使用」子开关（默认关，见 D1）。

理由：MCP 是「服务器级 enabledTools」，粒度是服务器；插件虽然也可以只做插件级，但插件通常一次性注册多个工具且能力差异大（比如一个插件同时提供「查文档」和「部署上线」），必须能只开前者。

**AI 可经 `app_control` 修改，但受四道约束**（本版决策：不列红线，改为「可改但每次审批」）：

1. **每次修改必弹审批**，且不得给出「本会话都允许」选项——扩权是低频高危操作，每次都要人看。
2. **单次只改一个插件**，禁止一次调用批量放开多个插件。
3. **全局总闸不可由 AI 打开**：AI 只能修改「总闸已开」前提下的插件级 / 工具级授权。否则 AI 可以先开总闸再逐项开，一次绕完三层。
4. **审批卡必须给出逐项 diff**：显示「query_quota：关 → 开」，而不是笼统的「修改插件工具授权」。

理由：让 AI 代劳是真实的便利性需求，可以给；但「AI 提议放宽自己的工具权限」这条链必须让用户看见**具体变更**并逐次确认。其中**第 3 条是关键**——没有它，前面三层授权会被「先把总闸打开」一步抵消。

### D4 审批：走同一条链，无例外

- 执行前走 `invokeWithApproval` 同一判定（与 `invokeMcpToolWithApproval` 共享逻辑，抽公共函数）。
- **禁止插件声明 `dangerous: true`**：不给任何「标记为危险以短路分类器」的位置。插件工具默认按「需要审批」处理，由用户的权限档与项目规则决定是否批量放行。
- 返回值形状对齐 MCP：`{ok, denied, message}`，前端据此区分「用户拒绝」与「调用失败」。
- **会话内允许**（`sessionAllow`）对插件工具同样生效——用户选「本会话都允许」是显式意图。

### D5 来源标记贯穿全链

| 位置 | 显示 |
| --- | --- |
| 工具定义 `description` 尾部 | 不下发来源（省 token，且模型不需要） |
| `<tool_catalog>` | 插件工具单列一组：`插件：<插件名> · tool_a / tool_b` |
| 工具卡（`ai-tool-cards.js`） | 卡头显示插件名 + 通用「插件」图标（图标名走 `core/icons.js`） |
| 审批卡 | 标题栏明示「插件 X 请求执行 tool_a」 |
| 操作留痕（`activity`） | subject 带插件 id，便于事后追溯 |
| 设置页授权列表 | 插件名 + 工具名 + 描述首行 |

### D6 子代理默认不可见

`frontend/src/ai/ai-subagents.js` 的 `subToolsForScope` 不注入插件工具。理由：子代理上下文更短、更难监督，且其结论会回流主代理——插件工具的副作用在子代理里发生更难归因。需要时由用户在主会话里调用。

### D7 失败与超时

- 插件 `execute` 抛错 → 转成工具错误结果回给模型（与内置工具一致），不中断回合。
- 超时：默认 60 秒（可配置上限 300 秒），超时后按失败返回，并提示「插件工具超时」。
- 插件执行期间会话停止（用户点停止）→ `ctx.signal` 触发，插件应尽快返回；不强制中断（插件可能在做不可中断的外部请求），但结果丢弃。

## 5. 授权 UI

位置：**设置 → AI → 权限 → 插件工具**（与 `appControlOn` 的 AI 工具开关同页，新增一个分组）。

```
插件工具 ⓘ                                 [全局总闸 ●○]

┌ ZCode 反代 v1.1.0                                    [允许此插件 ●○]
│  ☑ query_quota   查询剩余额度            [只读档可用 ☐]   ← 仅 readOnly 工具显示
│  ☐ deploy_service  部署服务（有副作用）
└
┌ 另一个插件 v0.3.0                                    [允许此插件 ○]
│  （未允许，工具不显示）
└
```

ⓘ 的气泡文案（`data-tip`，不占版面）：**插件代码与手动运行脚本权限相同；这里的开关只影响 AI 能否调用，不限制插件本身。**

交互要点：

- **全局总闸关闭时**，下面所有插件行置灰但**保留可见**（让用户知道这些能力存在）。总闸只能用户手动打开，AI 不可代开（D3 约束 3）。
- **「只读档可用」子开关只在工具声明了 `readOnly` 时出现**，默认关；勾上后该工具在只读档也会下发（D1）。这是「作者声明 + 用户确认」双人复核的落点。
- 插件禁用 / 卸载后其行消失；授权记录为内存态，随 `loadPlugins` 重建，不写 `ai-config.json`。
- 每个工具显示描述首行（截断 60 字），点击可展开完整描述——用户要知道自己授权了什么。
- 无工具注册的插件不显示行（避免噪音）。
- **AI 修改授权时的审批卡**（D3）：标题「插件 X 请求修改 AI 工具授权」，正文逐项列出 `工具名：关 → 开`，只出现一次确认按钮，**没有**「本会话都允许」。

## 6. 上限与拒绝策略

| 项 | 上限 | 超限行为 |
| --- | --- | --- |
| 单插件工具数 | 20 | 注册时报错（进 `lastLoadErrors`），不静默丢弃 |
| 全局插件工具数 | 50 | 同上 |
| `description` | 2000 字符 | 注册时报错 |
| `parameters` | 16 KiB | 注册时报错 |
| 工具名 | 64 字符 | 注册时报错 |
| 单次执行超时 | 默认 60s / 上限 300s | 超时按失败返回 |

原则：**注册期严格拒绝**（插件作者能立刻看到错误），**执行期宽容**（单次失败不影响其他工具与会话）。

## 8. 评审结论（2026-11-19 已定稿）

| # | 议题 | 决定 |
| --- | --- | --- |
| 1 | 下发边界 | **放宽一项**：允许插件声明 `readOnly` 的工具在只读档下发；但「声明」只是候选资格，须用户在授权 UI 显式勾「只读档可用」（默认关）。其余三项（默认关闭 / 计划模式不给 / 无 dangerous 捷径）保持不变 |
| 2 | 盲区声明位置 | **放安装插件确认框**。因「添加插件文件夹 / 导入 zip / 切换插件目录模式」没有确认框，补一个 `data-tip` 气泡兜底（不占版面） |
| 3 | 授权粒度 | **三层**（全局总闸 / 插件 / 工具）；声明 `readOnly` 的工具在工具级多一个「只读档可用」子开关 |
| 4 | 授权数据可否被 AI 改 | **可改，但受四道约束**：每次必弹审批且无批量放行、单次只改一个插件、**全局总闸不可代开**、审批卡给逐项 diff |

仍按现稿执行、无异议的部分：上限数值（§6）、子代理默认不可见（D6）、失败与超时口径（D7）、非目标（§9）。

**M2 状态：已定稿，可进 M3。**

## 9. 明确的非目标

- **不提供插件工具调用内置工具的代理能力**（不包装 `write_file` / `run_command`）——防止组合越权。
- **不做插件工具的沙箱**——插件代码本身就在同权限上下文里跑，给工具加沙箱挡不住插件自己干活，只会制造安全感错觉。
- **不做插件工具的模型侧分级**（比如「低风险工具自动放行」）——判定一律走既有的权限档 + 项目规则 + 端侧分类器，不新增第二套判定。
- **不在本轮设计插件工具的输出格式协商**（返回 string 或 `{text, images}` 即可，复杂结构让插件自己序列化）。
