# 用户委托代理（Delegate Agent）——有边界的授权委托方案

> 状态：**已评估 · 不做（2026-11-22 复评，见 §九）**——2026-11-22 从 `docs/unfinished-plans/` 移入本目录归档：决策已定、不会再产生实施动作，留作决策记录。其中「操作留痕 actor 失真」一项已拆出并单独实施（§9.4）。
> 一句话：不做「完全接管授权」，只在**明确白名单 + 额度 + 独立信息源**内代替人点头；**元权限（改权限档 / 改安全防线 / 改留痕 / 改委托配置本身）永不委托**。
> 需求原型：一个「用户智能体」，启用后接管所有需要用户拍板的环节（审批、隔离区、改会话权限等），且是应用级、跨会话、可完全接管。

---

## 一、背景与结论

### 1.1 需求本质

用户想要的是「少盯着点审批」。但需求描述里的「接管**所有**授权」「**完全**接管」「能改会话权限」三项叠加，实际是请求把系统的**信任根从「人」换成「另一个 AI」**。这不是普通功能开关，而是改变安全模型的根基。

### 1.2 评估结论

| 诉求 | 结论 |
|---|---|
| 完全接管所有审批 | ❌ 不做——被监管者不能监管自己，且现有 4 处全档必弹红线是作者反复加固的人工锚点 |
| 应用级、跨会话改权限 | ❌ 不做——这是「自我扩权」通道，代理可先给自己提权再让下游审批自动消失 |
| 减少审批打扰 | ✅ 做——以「有边界的委托代理」实现，只委托低风险、可回滚、可追责的部分 |

### 1.3 事实依据（为什么不能做完全接管）

仓库已有一次完整实证：`docs/reports/incident-2026-11-18-workspace-wipe.md`。红队会话在 full 档下写出 `find . -delete`，9 秒删光整个仓库（含 `.git`），当时唯一拦在前面的是人工审批与事后告警。事故报告第五节明确记录：「真正的逃逸面是脚本内再起 shell」——规则层只看 `run_command` 入参那一条命令，AI 自己写的脚本内 `execSync` 完全绕过判定。

当前「需要用户」的环节共 7 类，另有 5 道安全防线（完整取证见本次评估）：

- 7 类审批：命令 / 写文件 / 工作区外读取 / app_control 动作与危险设置项 / 计划批准 / worktree create·discard / 补丁回灌
- 5 道防线：权限档 `ai-constants.js:30`、分类器 `ai-permissions.js:297-316`、wipeguard `ai-wipeguard.js:436-442`、子代理沙箱 `ai-subagents.js:229-249`、操作留痕 `ai-panel.js:7057-7077`

**关键**：现有 full 档已「几乎全自动」，但仍刻意保留一批人工闸门：

- **危险命令单次确认**（`ai-permissions.js:254`）：注意它只在非 full 档生效（`dangerous && scope !== 'full'`）——full 档下危险命令是放行的，**这正是 2026-11-18 事故的直接机制**。
- **4 处全档必弹**（含完全权限）：worktree create/discard（`ai-panel.js:7159-7161`）、生命周期钩子（`main.js:1512-1513`）、补丁回灌（`ai-patch-card.js`）、`set_setting_row`（`main.js:1407`）。

「完全接管」本质就是突破这些专门设计成 AI 不能自己过的闸门。

## 二、设计原则（三条铁律）

### 铁律 1：被监管者不能监管自己——信息隔离

委托代理的判定依据必须是**结构化快照**（命令文本、cwd、diff、审批来源、风险标签），由宿主在审批点生成，**不得读取被监管会话可写的任何文件或上下文**。

- 反例（禁止）：代理去读 `.cadt/permissions.json`（`ai-permissions.js:1-4`）、读会话正文、读模型配置——这些都能被申请操作的 AI 改写。
- 正例：宿主把 `approval` 对象（`ai-panel.js:7829-7847` 的结构）序列化成只读快照传给代理；代理看不到发起会话的历史消息。

### 铁律 2：元权限不可委托——防自我扩权

以下操作**硬编码为不可委托**，不进配置、不给开关、代理不可见：

1. 修改任何会话的权限档（`setScope` `ai-panel.js:13364-13373`）
2. 修改分类器开关 / 阈值 / 权重（`config.autoClassifier` 等，`ai-permission-settings.js:530`）
3. 修改 wipeguard 配置 / 备份根 / 清理备份（`ai-wipeguard.js:247-270`、`WipeGuardClear`）
4. 修改操作留痕开关 / 清空留痕（`activityLog`、`ActivityClear`）
5. 修改委托配置本身（开关、白名单、额度、绑定模型）
6. 修改项目权限规则文件 `.cadt/permissions.json`

理由：这些是「审批的前提条件」。一旦可委托，代理只需先改这些，就能让所有下游审批自然消失——这不是接管审批，是接管审批的前提。

### 铁律 3：可撤销、可回放、有额度——可追责

- **额度**：委托授权带次数上限与时间窗（TTL），耗尽或过期自动退回人工，不静默续期。
- **撤销**：用户一键关闭即撤销全部在途委托；在途审批立即转回人工队列。
- **留痕**：委托决策单独记录（请求快照 + 代理理由 + 结果 + 时间戳），actor 标记为 `delegate`，与 `user`/`ai` 区分；该记录不可由任何 AI 工具清除。

## 三、委托边界：可委托 vs 不可委托

| 环节 | 可否委托 | 理由 |
|---|---|---|
| auto 档只读命令 / 已知安全命令族 | 无需委托 | 现状已自动放行（`ai-permissions.js:274-276`），再委托是多余 |
| auto 档非 risky 写文件 | 无需委托 | 现状已自动放行（`ai-permissions.js:265`） |
| 分类器已放行的低风险命令 | 无需委托 | 现状已自动放行（`ai-panel.js:7451-7458`） |
| **普通只读探索 / 查询 / 格式化** | ✅ 可委托 | 无副作用、可回滚 |
| **项目 allow 规则内的重复命令** | ✅ 可委托 | 用户已显式授权过同类 |
| 危险命令（`dangerous`/`singleUse`） | ❌ 不可委托 | 事故根因；`ai-permissions.js:254` 明确单次确认 |
| 脚本内起 shell 的场景 | ❌ 不可委托 | 规则层看不到，委托代理同样看不到 |
| 工作区外读取（工作区外路径审批） | ⚠️ 仅已批准读根内可委托 | 新路径必须人工 |
| worktree create / discard / export | ❌ 不可委托 | 会话级状态 + 磁盘级增删，`ai-panel.js:7159-7161` 全档必弹 |
| 补丁回灌应用 | ❌ 不可委托 | 隔离期唯一写主根通道，`ai-patch-card.js` 全档必弹 |
| `set_setting_row` / 生命周期钩子 / 插件 / MCP 配置 | ❌ 不可委托 | `main.js:1407/1512/1541`，一次性授权语义 |
| 计划批准（submit_plan） | ❌ 不可委托 | 计划是「人拍板方向」，委托它等于放弃目标控制权 |
| 元权限（第二节铁律 2 全部） | ❌ 永不可委托 | 防自我扩权 |

**设计取舍**：可委托白名单刻意保守——只放「现状本来就自动」和「无副作用/可回滚」两类。它带来的实际价值是「减少在已授权范围内的打扰」，而非「让 AI 自己决定危险操作」。

## 四、核心机制设计

### 4.1 委托授权配置（DelegationGrant）

**存储位置**：应用数据目录的 DPAPI 加密配置（复用 `internal/aiconfig` 的加密链），**不放工作区**（工作区可被 AI 写）。可在现有 `ai-config.json` 中新增 `delegation` 段，或独立 `delegation.json`（同样加密）。

结构（草案）：

```js
{
  version: 1,
  enabled: false,                    // 总开关，默认关
  allow: ['read', 'command-family'], // 可委托类型白名单（子集，红线项不接受）
  budget: { maxCalls: 20, windowMin: 60 },  // 时间窗内最大委托次数
  pinnedModelRef: '<profile-id>',    // 固定审批模型，防止被监管会话改
  snapshotRules: true,               // 决策依据用快照，不读实时规则文件
  createdAt: 0,
}
```

- `enabled=false` 默认，启用走 `set_setting_row` 同级风险的动作审批（人工确认）。
- `allow` 是白名单且**只能收窄**——传入红线项直接拒绝并报错，不静默忽略。
- `pinnedModelRef` 指向一个专用模型配置，该配置不允许被委托代理或被监管会话修改。

### 4.2 独立审批会话

委托代理是一个**应用级专用会话**，与业务会话隔离：

- 有独立的系统提示词，角色是「审批助手」，只输出 `approve` / `deny` + 简短理由，不调用任何工具。
- 输入只有宿主生成的结构化快照（命令文本、cwd、风险标签、diff 摘要、审批来源），**没有业务会话历史**。
- 不进会话搜索索引、不参与跨会话投递（`session_send` 对它不可用），避免被其他会话污染。
- 复用现有 `spawn_agent` 的会话运行时，但用 `sandbox: 'read'` 且工具集为空（只有回答能力）。

### 4.3 决策接线

在 `decideApproval`（`ai-panel.js:7865`）之前插入委托判定：

```
审批 pending
  → 是否命中不可委托红线？（硬编码判定）
      → 是：维持人工审批卡（现状不变）
  → 委托总开关开 + 类型在 allow 白名单 + 额度未耗尽？
      → 否：维持人工审批卡
  → 生成结构化快照 → 委托代理决策
      → approve：走与人工相同的落地路径，但 actor='delegate'
      → deny / 超时 / 异常：退回人工审批卡（fail-closed，绝不默认放行）
```

关键不变量：

- **fail-closed**：代理超时、返回歧义、格式错误，一律退回人工，不默认 approve。参考现有分类器 `ai-classifier-verdict.js:89-106` 的「只有明确 allow 才放行」语义。
- **红线判定在宿主侧**，不在代理侧——代理无法自己判断「这是否红线」，也就无法绕过。
- 委托决策走与人工相同的 `decideApproval` 落地路径（`ai-panel.js:7865-7950`），复用「记住」规则逻辑但 `remember` 强制为空（委托不落长期规则）。

### 4.4 留痕三态

现有留痕 actor 为 `user`/`ai`/`system`（`internal/activity/activity.go`），且 `logPermission` 把自动批准伪标成 `actor:'user'`（`ai-panel.js:7075`）——这是语义失真点，一并修正：

- 新增 `delegate` actor。
- 委托决策写独立记录：`{请求快照, 代理理由, 结果, 额度消耗, 时间戳, actor:'delegate'}`。
- 该记录走 `internal/activity/` 的追加链，但**不暴露 `ActivityClear` 给任何 AI 工具**；用户手动清留痕时委托记录单独保留或二次确认。

## 五、深入设计：自动批准能否委托？

这是本方案的核心问题。答案是：**现有「自动批准」已经覆盖了可安全委托的部分；剩下的「转人工」部分本质上不可委托。**

### 5.1 拆解现有自动批准的两类

系统里「自动批准」其实有两种完全不同的机制：

**A 类：规则型自动放行**（确定性，无模型判断）
- full 档直通（`ai-permissions.js:259`）
- 项目 allow 规则、会话 allow（`ai-permissions.js:257-258`）
- auto 档只读 / 家族 / gitFlowSafe 放行（`ai-permissions.js:274-276`）
- 这些是**人预先写下的规则**，确定性、可审计，不需要再委托给任何 AI。

**B 类：模型型自动放行**（分类器）
- 端侧线性 / 语义分类器 + 远程 AI 分类器（`ai-panel.js:7451-7491`）
- 输出危险概率 score，`score < 阈值` 才放行（`ai-permissions.js:297-316`）
- 关键设计：**无 deny 权、fail-closed**——只有明确低危才放行，任何异常/歧义/失败一律转人工（`ai-local-classifier.js:1-6`、`ai-classifier-verdict.js:1-8`）

### 5.2 为什么 B 类转人工的部分不能委托

分类器**转人工**的原因，恰恰是它判不准（`score ≥ 阈值`）或命中红线（危险命令、env 泄露 `ai-panel.js:7383-7388`、脚本档）。此时如果转给「用户智能体」（一个通用 LLM）：

1. **能力更强 ≠ 判得更准**：通用 LLM 比专用分类器更容易被上下文误导、更容易产生幻觉式「看起来安全」的判断；分类器至少输出可度量的 score 与阈值。
2. **丧失责任锚点**：分类器是确定性阈值 + 无 deny 权的设计，出事可追溯；通用 LLM 的自由文本理由无法作为可信审计依据。
3. **可被影响**：通用代理若能看到业务会话上下文（哪怕设计上隔离，实现也可能泄漏），就可能被申请操作的 AI 用提示注入诱导放行——这正是铁律 1 要防的。
4. **没有新增价值**：转人工的部分之所以保留人工，是因为「机器判不准 + 需要人担责」。换个机器判，两个问题都没解决。

### 5.3 结论

| 自动批准类型 | 是否委托 | 说明 |
|---|---|---|
| 规则型（full / allow / auto 只读） | 不委托 | 已是确定性自动，委托是多余 |
| 分类器已放行的低风险 | 不委托 | 已是模型自动，且是专用 fail-closed 模型 |
| 分类器转人工的 | **不可委托** | 转人工的原因就是机器判不准 + 需人担责；换通用 LLM 两个问题都没解决 |
| 红线项（危险命令 / worktree / 补丁 / 设置项） | **永不可委托** | 作者刻意保留的人工锚点 |

**因此**：「用户智能体」的正确定位不是「接管审批」，而是「在已授权范围内减少打扰」。要减少打扰，应该做的是——提升分类器准确率、扩大项目 allow 规则、提供批量/时间段授权，**而不是引入一个万能代理去替代人做本就判不准的判断**。

### 5.4 若用户仍坚持要「委托通用 LLM 判危险命令」

最低限度的护栏（仍不推荐）：

- 委托代理只能输出 `deny` 或 `ask-human`，**不能输出 `approve`**——即它只能「帮忙拦」，不能「帮忙放」。这样它再怎么被误导，最坏结果是多打扰一次，而不是放过一个危险操作。
- 所有危险命令仍需人工，代理只做「二次复核提示」。
- 这个「只拦不放」模式可以作为折中交付，但收益有限（分类器已经在做类似的「判不准转人工」）。

## 七、验证方式

1. **纯函数单测**（`ai-delegate.test.mjs`）：
   - 红线判定：危险命令 / worktree / 补丁 / 元权限全部返回「不可委托」
   - 白名单收窄：传入红线项被拒绝
   - 额度：耗尽后退回人工；TTL 过期退回人工
   - 快照脱敏：不含会话历史、不含规则文件原文
   - fail-closed：代理超时 / 歧义 / 异常一律 `ask-human`
2. **接线守卫**：`ai-app-actions.test.mjs`（若加动作）、`ai-tool-wiring.test.mjs`（工具描述与档位）、`no-src-tests`（测试位置）、`overlay-esc-guard`（若加弹层）全部通过。
3. **回归**：`cd frontend && npm test`（当前基线约 1613 项）；`go test ./... -timeout 300s`（后台执行，遵守 AGENTS.md「禁止前台阻塞」）。
4. **真机验收**（关键）：
   - 开启委托后，普通只读命令走代理、人工审批卡不再弹出
   - 危险命令 `find . -delete` 仍弹人工卡（红线不被委托）
   - worktree create/discard 仍弹人工卡
   - 委托额度耗尽后自动退回人工
   - 一键撤销后所有在途委托立即转人工
   - 留痕中委托决策 actor 为 `delegate`，且 AI 工具无法清除

## 八、分期与风险

### 分期

- **P0 决策内核**：红线判定 + 快照 + 额度 + fail-closed 纯函数与单测（无 UI、无接线）
- **P1 委托代理会话**：独立会话 + 工具集为空 + 系统提示词
- **P2 接线**：`decideApproval` 分流 + actor 三态留痕
- **P3 配置与 UI**：设置页 + 导入导出 + 一键撤销
- **P4 真机验收 + 归档**

### 主要风险

| 风险 | 缓解 |
|---|---|
| 委托代理被提示注入诱导放行 | 信息隔离（铁律 1）+ 红线宿主侧判定 + 只委托无副作用/可回滚项 |
| 代理自我扩权 | 元权限硬编码不可委托（铁律 2）+ 配置存加密应用数据目录 |
| 责任不清 | actor 三态 + 独立留痕 + 不可由 AI 清除 |
| 用户误解为「完全接管」 | 设置页文案明确「仅低风险委托，红线仍需人工」；文档与 CHANGELOG 同步 |
| 与现有 auto 档功能重叠 | 第三节白名单刻意只放「现状已自动」和「无副作用」——若重叠严重，**优先放弃本方案，转而优化分类器/allow 规则** |

### 最终建议

若用户的真实诉求是「少点审批」，**优先做「扩大 allow 规则 + 提升分类器准确率 + 批量/时间段授权」，成本更低、风险为零、已有基础设施**。本方案（委托代理）只在用户明确需要「让另一个模型复核并点头」时才值得投入，且必须守住三条铁律与「只委托、不接管」的定位。

## 九、复评（2026-11-22）

> 复评触因：距初稿 4 天，需确认结论是否仍成立。以下全部为当前工作区实测。

### 9.1 结论

**不做。** 三条铁律与「只委托、不接管」的定位是对的，但**净价值为 0**——白名单放的东西现状已经自动放行，放不掉的东西正是作者刻意保留的人工锚点。复评新增两条比初稿更硬的论据（9.3 第 2、3 条）。

### 9.3 新增论据

1. **白名单的实际减扰增量为 0。** §3 里唯一标 ✅ 的两项（普通只读探索、项目 allow 内的重复命令）在 auto 档已由 `gitFlowSafe / readOnly / familyAuto / classifier` 四条通道自动放行（`ai-permissions.js:274-280`）。read 档下它们仍弹卡，但 read 档用户切 auto 档即得同等效果——委托代理新增的能力等价于「一个已有的开关」，代价却是**多一个信任根**。

2. **人工锚点在变多，委托的红线表就得永久跟着长。** 4 天里新增 3 个必弹点。每加一个，委托代理都必须同步排除，漏一处就等于给新防线开了后门；这类维护成本随功能增长单调恶化，且失效是静默的。

3. **项目实际走的正是初稿推荐的替代路线，并且奏效了。** 这轮真正解决审批疲劳的改动是「`cd x && npm test` 不再反复弹卡」——扩 `commandFamilySignature` 容忍一段前置 `cd`，加上工具描述引导用 `cwd` 参数（CHANGELOG「改进（自动审批档…）」一节）。低成本、零新信任根、当天生效。这与 §277 的优先级判断一致，等于用实践否决了本方案的价值主张。

### 9.4 唯一值得单独做的事：留痕 actor 失真

初稿 §4.4 把这个当「顺带修正」埋在委托方案里，但它**与委托无关、可独立交付、零风险**：

- `logPermission`（`ai-panel.js:7324-7330`）把 allow/deny 一律写 `actor:'user'`，只有 `source` 区分来源。
- 操作留痕页按 actor 打徽标并支持筛选（`settings/activity-pane.js:130` 的 `ACTIVITY_ACTOR_LABEL = {user:'用户', ai:'AI', system:'系统'}`、`:177`）。结果是**规则放行 / 家族放行 / 分类器放行 / 完全权限直通的每一笔，在审计里都显示成「用户批准」**。
- 修法：按 `source` 映射 actor（`scope` / `project` / `user` 归 user；`readonly` / `family` / `git-flow` / `classifier` / `local-classifier` / `full` / `auto` 归 ai），`validActivityActor` 已支持 `ai`，**无 Go 变更、无 schema 变更**；配一条纯函数 + 单测。约 10 行。
- 价值：审计可读性（「谁批的」不再骗人），也是将来任何授权机制的前置条件。
- **已实施（2026-11-22）**：纯函数 `permissionAuditActor(source)` 落在 `frontend/src/ai/ai-permissions.js`（映射表 + 未知来源归 `ai`——宁可少记人的功劳，也不能把自动放行记成人工批准），`logPermission` 改用它；测试见 `frontend/test/ai/ai-permissions.test.mjs` 的「留痕 actor」两例（逐来源归属 + 与 `decidePermission` 实际产出对齐）。`agent-worktree` / `worktree-isolation` / web 内置 `default` 归 `system`。
